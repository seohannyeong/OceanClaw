# 절차 제목 및 인접 문맥 보완 실험

## 구현

`scripts/compare_chunk_context.py`에서 PDF 책갈피(outline)를 pypdf로 읽고, 책갈피의 페이지 및 제목을 기존 추출 텍스트 위치와 연결했다.
질문별 하드코딩, LLM 요약, 수동 정답 추가 없이 문서 전체 270개 청크를 처리했다.
기존 청크 본문/ID/페이지를 그대로 유지하고 별도 필드만 추가했다.

- `sections`: 해당 청크에 겹치는 절차 ID, 제목 경로, 원문 위치와 텍스트
- `embedding_text`: 제목 경로 + 원래 청크 본문

예시:

```text
INSPECTION AND MAINTENANCE > MAINTENANCE PROCEDURES > Replace Engine Oil Filter

... Manually tighten ... then tighten by a further 3/4 of a turn.
```

제목이 다른 원래 청크로 분리되어 있던 `p73-c3`에도 오일 필터 제목이 연결됐다.
연료 필터 `p77-c3`에는 Fuel Filter Change가 연결됐다.
책갈피의 계층을 그대로 사용하므로 상위 제목이 항상 정확한 장비 분류 체계인 것은 아니다.
여러 절차가 섞인 청크에는 여러 제목 경로가 붙는다. 이번에는 본문을 다시 나누지 않았다.

책갈피 중 표지의 COVER만 본문과 일치하지 않았다. 제목이 없는 표지/서문 6개 청크는 원문만 사용했다.
책갈피가 없는 다른 PDF는 자동으로 같은 효과를 얻을 수 없다. 제목 검출 방식을 별도로 마련해야 한다.

## 인접 문맥 정책

검색된 seed 3개는 원래 본문을 유지한다.
각 seed의 바로 앞/뒤 청크 중 같은 파일, 같은 페이지, 같은 절차 ID에 해당하는 부분만 추가한다.
인접 청크가 여러 절차를 포함하면 일치하는 절차 부분만 잘라서 추가한다.
추가된 이웃에서 다시 이웃을 찾지 않고, 페이지를 넘는 연결도 하지 않는다.
원래 seed 자체가 여러 절차를 포함하는 문제는 그대로 남아 있다.

본문/ID를 보존했으므로 기존 정답 청크 라벨로 직접 비교할 수 있다.
이웃 문맥은 청크 ID뿐 아니라 정답 근거 문장까지 실제로 포함해야 성공 처리한다.

## 통제 조건

- BGE-M3와 한국어 원문 질문 30개 유지
- 질문 임베딩은 한 번 계산해 두 인덱스에 동일하게 사용
- 번역, 규칙 확장, reranker, 표 구조화는 적용하지 않음
- 새 인덱스에 제목을 추가한 문서 벡터만 별도로 생성
- 같은 절차의 이웃 확장은 기존/제목 인덱스 양쪽에서 따로 평가
- 기존 데이터/기본 인덱스/BGE-M3 기준 인덱스/PDF 해시 변경 없음
- 현재 모델 digest가 이전 비교 실행과 같음을 검사

이번 질문은 이미 실패 분석에 사용된 개발용 평가 질문이다. 최종 일반화 성능은 새 질문으로 검증해야 한다.

## 결과

| 구성 | 정답 근거 포함 질문 | 해석 |
|---|---:|---|
| 기존 BGE-M3 Top-3 | 19/30 (63.3%) | 기존 기준선 재현 |
| 제목 추가 BGE-M3 Top-3 | 21/30 (70.0%) | 같은 3개 검색 결과에서 2개 개선 |
| 기존 Top-3 + 같은 절차 이웃 | 20/30 (66.7%) | 확장된 문맥의 근거 포함률 |
| 제목 Top-3 + 같은 절차 이웃 | 22/30 (73.3%) | 확장된 문맥의 근거 포함률 |

제목 추가 후 개선된 질문은 q06(오일 필터 추가 회전 수), q19(열교환기 체결 세기)다.
제목 검색에 이웃 문맥을 추가하면 q03(연료 필터 씰)이 추가로 포함된다.
기존에 성공했던 19개 질문은 제목 추가 후에도 모두 성공했다.
MRR@3는 0.544에서 0.617로 변했다.

22/30은 Hit@3가 아니다. 검색한 3개 청크 이외의 원문을 더 가져온 상태에서의 근거 포함률이다.
평균 원문 문맥량은 제목 seed 기준 약 2,082자에서 이웃 포함 약 3,835자로 증가했다(중복 overlap 포함).
평균 6.7개 문맥 조각을 가져왔다. 더 많은 문맥은 답변 생성 시간과 메모리 부담을 늘릴 수 있다.
이번에 최종 LLM 답변을 생성하지 않았으므로 답변 품질/지연 개선으로 해석할 수 없다.

q11, q13, q14, q16, q18, q22, q24, q26은 제목과 이웃만으로 해결되지 않았다.
제목 추가의 효과는 확인했지만 모든 검색 문제를 해결하지는 못했다.

## 파일과 실행

- 새 인덱스: `index/bge_m3_titles_20260910_213358/pdf.faiss`
- 새 메타데이터: `index/bge_m3_titles_20260910_213358/pdf_docs.json`
- 제목 부착 청크: `output/eval/chunk_context_20260910_213358/titled_chunks.jsonl`
- 검색/확장 원문: `output/eval/chunk_context_20260910_213358/results.jsonl`
- 집계: `output/eval/chunk_context_20260910_213358/summary.json`
- 제목 매칭 검사: `output/eval/chunk_context_20260910_213358/heading_audit.json`

```powershell
python scripts\compare_chunk_context.py
python scripts\test_chunk_context.py
```

다시 실행하면 새 시각의 폴더에 인덱스를 새로 구축하고 평가한다. 기존 파일은 덮어쓰지 않는다.
이 스크립트는 이번 단일 PDF와 고정 벤치마크를 위한 실험 도구이며 `/ask`의 기본 검색 흐름은 변경하지 않았다.
다음 배포 단계에서는 제목 인덱스 로딩 및 같은 절차 문맥 확장을 서비스 옵션으로 연결하고, 문맥 길이 제한과 새 질문 평가를 추가해야 한다.
