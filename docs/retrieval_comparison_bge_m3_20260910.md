# BGE-M3 다국어 검색 비교 결과

## 무엇을 했나

기존 영어 PDF 청크 270개를 수정하지 않고 BGE-M3로 다시 임베딩했다.
`index/bge_m3/pdf.faiss`와 `index/bge_m3/pdf_docs.json`에 별도로 저장했다.
기존 `index/pdf.faiss`와 문서 메타데이터, PDF 추출 결과, 청크, 평가 질문의 해시가 변경되지 않았음을 확인했다.
새 인덱스는 270개 × 1,024차원이며 모든 값이 유한하고 각 벡터의 L2 norm이 약 1이다.

같은 질문 30개를 원문, 규칙 확장, 영어 번역, BGE-M3 원문 검색으로 총 120회 실행했다.
모든 검색 요청이 성공했다. 답변 생성과 실제 서비스 기본 모델 교체는 수행하지 않았다.

실행 결과: `output/eval/20260910_211707_618252/`

## 검색 결과

| 방식 | 정답 근거 Hit@3 | MRR@3 | 소요 시간 중앙값 | 평균 |
|---|---:|---:|---:|---:|
| 한국어 원문 + nomic | 0/30 (0%) | 0.000 | 0.012초 | 0.014초 |
| 규칙 확장 + nomic | 4/30 (13.3%) | 0.094 | 0.014초 | 0.187초 |
| 영어 번역 + nomic | 21/30 (70.0%) | 0.644 | 0.539초 | 1.939초 |
| 한국어 원문 + BGE-M3 | 19/30 (63.3%) | 0.544 | 0.038초 | 0.041초 |

정답 근거 문장을 포함하는 청크가 상위 3개에 있는지 자동 평가했다. 특정 페이지를 찾는 것만으로 성공 처리하지 않았다.
이 수치는 30개 초기 질문에서의 결과이며 전체 서비스 정확도나 정비 답변 정확도가 아니다.
동등한 근거를 가진 다른 페이지/청크가 자동 평가에서 누락될 수 있으므로 최종 성능에는 수동 검수가 필요하다.

## 서로 다른 성공 사례

- BGE-M3만 성공: q08(작동 중 배터리 단자 분리), q12(냉각액 높이).
- 번역만 성공: q03(연료 필터 씰), q19(열교환기 체결 세기), q22(공기 여과기 청소 방향), q24(웨이스트게이트 레버).
- 둘 다 실패: q06, q11, q13, q14, q16, q18, q26.

이번 결과만으로 번역과 BGE-M3 중 하나가 모든 질문에서 더 좋다고 할 수 없다.
두 방식의 검색 결과를 합치는 방법도 후보지만, 아직 병합·재정렬한 실제 Top-3 실험은 하지 않았다.
두 방식 중 하나라도 성공한 질문 수를 Hybrid Search의 성능이라고 표시해서는 안 된다.

## 번역 오류 검토

| 질문 | 관측한 번역 문제 | 번역 검색 | BGE-M3 검색 |
|---|---|---|---|
| q11 윤활유 양 측정 | `apply lubricant`로 번역해 도포로 의미 변경 | 실패 | 실패 |
| q12 냉각액 높이 | 높이 대신 온도를 질문 | 실패 | 성공 |
| q14 축전지 액체 부족 | `capacitor`, `leaking`으로 장비와 상태 변경 | 실패 | 실패 |
| q18 축전지 분리 | `capacitors`로 장비 오역 | 실패 | 실패 |
| q19 나사를 죄는 세기 | 어떤 나사를 죌지로 질문 변경 | 성공 | 실패 |

검색에 성공해도 번역이 정확하다는 뜻은 아니다. q19가 그 예다.
BGE-M3는 번역 단계를 생략하지만 의미 검색 오류까지 사라지는 것은 아니다.
번역의 원문 보존 프롬프트는 이전 실험과 동일하게 유지했다.

## 모델 메모리 관측

Ollama `/api/ps`를 번역 직후와 검색 직후에 총 150회 조회했으며 조회 실패는 없었다.
다음은 모델별 로드 크기와 VRAM의 관측 최댓값이다. GiB는 1,024^3 bytes 기준이다.

| 모델 | 로드 크기 | VRAM |
|---|---:|---:|
| nomic-embed-text | 약 0.455 GiB | 약 0.455 GiB |
| bge-m3 | 약 0.868 GiB | 약 0.868 GiB |
| gemma3:4b | 약 3.686 GiB | 약 3.686 GiB |

로드 크기에 VRAM이 포함되므로 두 값을 더하지 않는다. 다른 모델도 함께 로드되어 있었고, 이 값은 프로세스 피크 RSS나 시스템 전체 메모리가 아니다.
BGE-M3는 nomic보다 임베딩 모델의 메모리 요구가 크지만, 검색을 위해 번역 LLM을 호출할 필요는 없다.
다만 최종 RAG 답변 생성에는 여전히 chat 모델이 필요하므로 전체 OceanClaw에서 gemma3의 메모리가 사라진다고 해석하면 안 된다.
이는 Windows 데스크탑 실측이다. Jetson 8GB에서의 성공 여부, 최고 메모리, 응답 시간은 아직 검증하지 않았다.

## 시간 측정 조건

- 같은 실행에서 네 방식의 순서를 seed=42로 섞었다.
- 전체 시간은 질문 변환, 질문 임베딩, 정규화, FAISS 검색, 결과 조립이다. 최종 답변 생성은 포함하지 않는다.
- 인덱스 초기 로딩과 `/api/ps` 관측 요청 시간은 제외했다.
- BGE-M3는 직전 인덱스 생성으로 이미 로드된 상태였다.
- 최초 nomic 요청은 약 5.14초, 최초 번역 요청은 약 40.95초여서 평균에 큰 영향을 주었다.
- 중앙값은 이번 실행의 보통 요청을 설명하는 참고값이며, 통제된 워밍업/콜드 스타트 반복 비교는 아니다.
- 특정 배수의 속도 향상을 제품 성능으로 주장하지 않는다. Jetson에서 따로 반복 측정해야 한다.

## 판단과 다음 작업

현재 규칙 확장보다 BGE-M3가 더 많은 질문에서 근거를 찾았으며 번역을 생략할 수 있다는 장점이 있다.
영어 번역은 이번 질문에서 2개 더 성공했고 MRR도 높았다. 한 번의 소규모 평가만으로 최종 우승 모델을 확정하지 않는다.
실제 서비스 모델은 그대로 유지했다. 우선 두 방식 모두 실패한 질문의 검색 원문과 라벨을 검토하고, 새로운 질문으로 비교를 반복하는 것이 타당하다.
Jetson 배포 후보로 BGE-M3를 검토하되 같은 인덱스로 질의 검색과 답변 생성을 함께 실행하며 `tegrastats`를 확인해야 한다.

## 재실행

```powershell
python scripts\compare_retrieval.py --modes original expanded translated multilingual
```

새 출력 폴더에 저장하므로 이번 결과를 덮어쓰지 않는다.
실험 조건, 설치 모델 digest, 플랫폼, 입력/코드 해시는 `manifest.json`에서 확인할 수 있다.
입력 무결성은 `integrity.json`, 상세 메모리는 `memory_summary.json`, 질문별 비교는 `comparison.csv`, 원문 근거는 `results.jsonl`에 있다.
